# 网关展示名升级

本次新增 `display_name` 和 `display_name_en` 两列独立唯一索引。默认名回填为去除首尾空白的技术名；英文名初始化为 NULL。此迁移要求停止网关写入，不能让旧 Dashboard 与新代码交替写入同一数据库。

## 发布顺序

1. 备份数据库，记录当前迁移状态。在同版本 MySQL 和实际数据副本上演练 `core.0057_gateway_display_names`，排查空名称、超过 64 字符、去除首尾空白或按数据库排序规则比较后重复的技术名。冲突须在正式迁移前处理。
2. 在执行迁移前暂停 Web 网关写操作、Open/Sync 自动注册、SaaS 部署同步、Admin、管理命令和会写网关的后台任务。等待在途请求/任务完成，停止所有旧 Dashboard 写入实例，禁止其自动重启。仅停前端页面不足以停止自动同步。
3. 保持停写，使用新版本执行正常升级迁移。0057 先添加字段、再回填默认名、最后建立默认名唯一约束；回填与建约束之间不得插入新网关。MySQL DDL 不能依赖整段事务回滚。
4. 检查迁移记录和实际表结构：两列及各自唯一索引已建立，默认名均已回填、无空值，英文名允许多个 NULL。确认所有写入实例、后台任务和管理命令均已切换到新版本。
5. 完成前后端联调：读取 `display_name` 随请求语言变化，Web 写入同名字段只修改默认名；前端须按此契约一同切换。验证创建、修改、同列冲突提示、模糊搜索和 Sync 后再恢复写入及自动化部署。

## 写入与兼容性边界

- `display_name` 仅与同列查重，非 NULL 的 `display_name_en` 仅与同列查重；允许与其他列或技术名相同。
- 默认名省略/清空时的回填值仍须唯一。若其他网关已使用 `foo-gateway` 作为默认名，新建技术名 `foo-gateway` 必须显式提供另一个可用默认名。
- Web、Admin 不提供英文名编辑。Sync V1/V2 省略、清空或传 NULL 都会清除英文名；旧客户端每次同步也会清除它。需要保留英文名的自动化配置应每次显式传入。
- 入口执行格式/可用性预检查，数据库唯一索引处理并发竞争。模型 `save()` 仅做字段规范化，不做查重或名称快照。Web/Sync 通过显式 `update_fields` 保留省略字段；直接 ORM 保存遵循 Django 行为，调用者需要部分写入时应指定 `update_fields`。
- `name + fuzzy=true`、`keyword` 和 `query` 的既有模糊搜索增加两个展示字段；精确技术名/ID 查询仍按原定义工作。

## 失败处理

迁移或检查失败时保持停写，不得恢复旧写入实例。先核对迁移记录和实际字段/索引状态；MySQL 已完成的 DDL 可能保留，不能直接反复执行迁移或使用 `--fake` 掩盖差异。根据已备份状态修复后继续，或恢复一致的数据库备份与旧代码。

新版本恢复写入后，如需回滚，应重新停写并制定数据保留方案；直接逆迁移会删除新展示名，恢复旧备份会丢失备份后的写入。本文描述发布要求，不代表已完成生产迁移或前端联调。
